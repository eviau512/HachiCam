# rc22：继续 GPU 迁移与灯具拒绝证据

日期：2026-10-18。遵循问题 → 权威规格 → 修订规格 → 实现/验证。
本轮完成局部物理验证的实验性 Vulkan 路径与分层诊断；**没有声称灯具方块已修复，
也没有声称手机处理明显加速**。测试包交付记录在文末。

## 问题与规格

[灯具研究](LAMP_HDR_ALGORITHM_RESEARCH_2026-10-18.zh-CN.md) 已证实：近/远两组最短帧
有灯罩轮廓，旧输出的矩形边界对应 256 网格节点 +141。柔边不能恢复灯罩，
绕过局部几何的离线 Mertens 也不满足生产准入。继续保留 SPEC_02 的 HDR-SEAM-22
和未裁切通道保护，未放宽 0.80/0.90 相关性、0.68 细节或 1.5 px 冲突门槛。

先修订 SPEC_02 的 rc22 实施切片，再实现独立 GPU 物理检查。目的包括继续卸载计算，
也包括分开量测拟合和验证，避免把所有局部耗时都归因于像素检查。

## 实现

- 将局部 ECC 提案与物理验证拆开，分批上传测量区域。GPU 完成平移采样、掩码与
  两级中心化方差/协方差归约；CPU 接收有限统计，保留原准入与失败补齐。
- 每批最多 64 个 <=321×321 区域，逻辑空间约 56.3 MB；实际分配受共享 64 MiB
  上限约束。ECC 自身仍为原 16 区域上限。拒绝整图 50 MP 浮点金字塔。
- 单工作组覆盖整区域的早期版本成本过高，已改为 1024 像素局部归约再合并统计。
  参数边界、低信号抵消、异常结果使用原 CPU 检查；GPU 拟合未通过物理检查时
  仍重跑原 CPU ECC，不能把不合格 GPU 提案直接入片。
- 新增独立的 base/highlight、尺寸及批量成本档。校准包含打包/传输、执行、回读和
  CPU 补齐；不够快就用 CPU，校准中已算出的 CPU 结果复用。
- `backendDecisions` 的既有有界记录增加 `local-validation-v1`：拟合/验证耗时、
  GPU 检查、CPU 补齐、低信号、identity、mask、ECC、transform、correlation、detail、
  admitted 计数。`nativePerformance.gpuPhysicalCheckVersion=batched-physical-v1`；
  streaming 为 not-used。不创建旧 `capture/` 目录。
- release 保持 CPU；原生高像素 streaming 的逐区域检查仍 CPU，此轮不能称全链 GPU 化。

宿主 OpenCV 5 的浮点采样与 Android 4.10 的 1/32 坐标采样不同，不能让宿主测试掩盖
手机路径的数值差异。版本路径明确分开，另在实际 GPU 上执行 Android 量化分支。
依据与对照：[OpenCV 4.10 实现](https://raw.githubusercontent.com/opencv/opencv/4.10.0/modules/imgproc/src/imgwarp.cpp)、
[OpenCV 5 实现](https://raw.githubusercontent.com/opencv/opencv/5.x/modules/imgproc/src/imgwarp.cpp)。

## 已执行验证及其边界

- CPU 原生完整回归通过：局部配准、视差、遮挡、模糊、噪声、高光、参考排序、
  HDR/SR、裁切、文档边界与 streaming。
- 实际硬件 GPU 基础/完整图像检查通过；新核覆盖 >64 区域、多批/边缘/非连续行、
  正负亚像素、Android 量化分支、计数/相关性/细节阈值、低信号/全平与非法输入。
  原九类失败/能力限制与共享资源隔离检查通过。CPU 回退不算 GPU 执行。
- 六组冻结 CPU 成片与旧版逐字节相同：本次近/远灯、旧暗屏、明亮 PPT、远拍 PPT、
  旧卧室灯。自动后端仍有既有拟合/资格的微小变化，不能只靠文件哈希宣称质量提升。
- 手机实际采用、温度、完整等待、持续负载和成像验收尚待新包日志；宿主不是手机计时。

## 性能结果与新定位

最终版本每组同进程 3 次自动后端重放，首轮单列，后两轮只作小样本观察。
旧/新都包含实际后端校准。不存在所有场景稳定的整体提速，不能标记 30% 目标完成。
完整冻结记录保留在本机 `.tools/rc22-final-bench.json`。

| 场景 | 旧首轮 /新首轮 | 旧后两轮中位 /新后两轮中位 | 后两轮变化 |
| --- | --- | --- | --- |
| 近灯 | 13.469 /14.047 s | 10.886 /11.173 s | +2.63% |
| 远灯 | 8.734 /8.388 s | 6.217 /5.896 s | -5.16% |
| PPT | 8.584 /9.156 s | 6.314 /6.314 s | 约 0% |

最终这三组首轮自动成片均与对应旧版逐字节相同，资格 tile 分别仍为 512 /0 /110。
中间开发重放曾有 PPT 最大 47 级、99 百分位 0 的局部差异，相关自动拟合/资格路由
对成本校准有依赖；最终一致不能代替所有设备与热态的成像验收。

宿主新物理路径在这些生产重放中由于完整成本仍选择 CPU。实际 GPU 核与全图集成已被
强制硬件测试覆盖，但这不意味着这些自动重放正式采用了新核。手机必须重新实测选择。

新分层记录表明，近组 base 提案阶段约 0.33–0.48 s/张，热态物理验证约 0.028 s/张；
短帧提案约 0.26–0.38 s/张，验证约 0.007–0.008 s/张。远组最短帧 12 个提案中，
9 个未通过相关性、3 个未通过细节；支持为 0 并非简单全局配准失败。
这些是宿主局部测量，不能代替手机上数秒的拟合耗时。

因此后续优先处理 CPU ECC 补齐/弱候选与驻留准备平面，再做跨曝光响应和连续融合，
不再假定只迁移最终统计就能消除主要等待。基于 JPEG 的原始亮度差仍会使最短帧
局部比较失真；跨 bracket 几何链需要独立验证，不能拿一张全局变换直接绕过局部资格。
