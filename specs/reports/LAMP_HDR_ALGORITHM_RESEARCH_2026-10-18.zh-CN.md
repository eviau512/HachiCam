# 台灯方块、轮廓恢复与空间连续 HDR 研究

2026-10-18；当前成像实现为 rc21，源码 `6dc065c`，研究基线 `eb145a4`。
本轮交付是证据、算法评估、离线实验及规格修订，没有替换 App 成像算法或构建新 APK。
按分析问题 → 分析规格 → 修订 SPEC_02 → 离线候选实验的顺序执行。

## 1. 证据与结论

`hachicam_capture_20261018_172312_5ea2f24a.zip`：79,684,833 字节，稳定性和全部 CRC 通过；
SHA-256 `74363fafad007795ee1218345971143e3fc9a2a525b14105aa1018511c2ced77`。
按 captureId 区分两组，而非将最新 ZIP 当成只有一张照片：

| 场景 | captureId 前缀 | HachiCam 来源 / 成片 | 原生内部 / 全局 / 局部 | 完整诊断快照等待 |
| --- | --- | --- | --- | --- |
| 近处灯具 | `fbb12aef` | 4096×3072 →8140×6092，49.589 MP | 36.114 /6.650 /16.404 s | 41.197 s |
| 远处房间 | `9ff74266`，最新 | 4096×3072 →4076×3052，12.440 MP | 20.280 /7.317 /8.556 s | 25.192 s |

近处为 12.6 MP 来源上的 2x 输出，实际重建改动约 2.212%；不是原生 50 MP 采集。
远处 0 个合格重建块，因此保持原生尺寸。包内两组 ZIP 负载写入约 0.344 s。

**两组原始最短帧都拍到了完整灯罩轮廓**。近处基线约 33.333ms /ISO793，最短帧
约 4.103ms /ISO101；远处基线约 24.991ms /ISO1939，最短帧约 7.556ms /ISO100。
实际曝光积比均约 64 倍，即约 6 EV。这次不是所有输入都已经丢失了灯罩信息。
现有 JPEG 合成没有充分利用这些观察，提高输出像素或单纯锐化不能解决。

远处手机日志明确记录最短帧全局对齐后局部支持为 **0**，没有合格局部节点，最终未采用；
不能误写为“没有拍最短帧”或“全局配准失败”。近处该帧虽然进入了高光路径，其完整
轮廓也没有在成片中保留下来。两组最终的 partial_highlight_recovery 标签并不等于灯具 ROI 验收。

## 2. 方块来源的定位

现有 `LocalRegistration` 默认节点间距 **256 来源像素**。高光模式从附近合格节点中
选最近者，只在相距各轴 <=140 像素的矩形内给支持；邻点位移冲突 >1.5 像素拒绝。
`supportPixel`、最终采用短帧及 247 通道阈值又是硬切换。格子边界因此可能进入辐射合成，
即使局部几何本身有合理的防错意图。

在忽略目录复制当前生产源，只增加中间量记录，冻结相同七张解码输入运行 CPU 路径：

- 近处在 **原生 HDR 后、超分和 JPEG 编码前**出现方块；前 HDR 图没有这些直角边界。
- 新垂直边界包括来源 x=**3213、3469、3725**，分别对应节点 3072/3328/3584 的 +141；
  新水平边界 y=**653、909、1165** 对应节点 512/768/1024 的 +141。
- 远处也出现来源 x=**2189** 的新边界，对应节点 2048+141。
- 近处最短帧的宿主测量只有一个合格节点 `(3072,1024)`；它在固定灯具/光晕 ROI
  `(3000,500,1096,1050)` 的 gate 覆盖仅约 **3.96%**。远处此帧没有合格节点，和手机日志一致。

这给出了矩形支持机制的因果证据，不能把问题归给 64 像素 SR tile 或 JPEG 的 8×8 编码块。
宿主 OpenCV 5 与手机 OpenCV 4.10、CPU/GPU 路由的输出略有差异，近处宿主只实际采用
两张高光而手机报告三张；不声称宿主每个像素/资格都与手机相同。矩形边界产生于现有
生产公式及支持范围，和用户成片的形状相符。

另一个独立问题是 JPEG 响应：远处手机的两张轻度短帧，metadataGain 约 **5.661**，
估计 responseGain 却为 **38.870/41.181**。宿主近处约 **42.689/40.811** 对 metadataGain
约 5.65。跨曝光 JPEG 已经过 ISP 的不同映射，不能将一个全图标量当作已标定辐射，也
不能简单强制改回曝光积比。这同时影响几何验证的比较域与高光色调。

## 3. 哪些算法值得采用

以下为公开算法与独立工程方案，没有证据证明它们就是 MotoCam 的私有实现。

| 方案 | 主要作用 | 对本项目的判断与 GPU 适配 |
| --- | --- | --- |
| 重叠窗口、归一化连续权重 | 分区仅用于计算，输出在重叠范围内连续；不在节点矩形边缘硬替换 | **最先做**，但需先补齐可靠几何支持；不能把权重平滑进未知/冲突区域。逐像素权重与合成适合 GPU |
| Guided Filter / 双边网格 | 沿真实物体边界平滑置信度、响应或增益场，避免把灯与墙混在一起 | **高优先**。参考已白掉时必须用有效短曝光/合成引导，不能只用平白的参考图；box/separable filter 或 grid 适合 GPU |
| Laplacian 金字塔多尺度曝光融合 | 大尺度平滑亮度过渡，小尺度保留轮廓与纹理，降低拼接感 | **高可行，但不能原样全局替换**。需运动/噪声/颜色与参考保护；优先原生尺寸 ROI+halo/GPU，不建每帧 50 MP 全图浮点金字塔 |
| 自适应四叉树 / 多级重叠网格 | 在亮度梯度、裁切边缘或不确定处细分，其他区域保持粗网格 | **辅助调度方案**。只减块大小仍可能产生更密接缝；采样间距与对齐上下文尺寸应分开，不可让细块失去周围有效结构 |
| SLIC/SNIC 超像素 | 让区域边界跟随颜色/空间结构 | 可研究，当前不优先：白掉的参考不含真实灯罩边界，分割不能恢复缺失观察；还要管理不规则区域开销与纹理过分割 |
| RAW HDR / 欠曝基准连拍及后续 tone mapping | 尽早保留高光、降低跨 JPEG 响应歧义，再合并阴影信息 | 中期结构改进，取决于公开能力和资源。当前两组短 JPEG 已有轮廓，因此当前问题不必等 RAW 才能推进 |

[Mertens 等的 Exposure Fusion](https://www.tommertens.com/old-academic/papers/exposure_fusion_reduced.pdf)
按图像质量权重进行多尺度融合，假定输入已经对齐；这不是运动/遮挡验证的替代物。
[Guided Filter](https://people.csail.mit.edu/kaiming/eccv10/index.html) 使用引导图控制保边平滑，
[双边网格](https://groups.csail.mit.edu/graphics/bilagrid/) 适合并行保边运算。
[Durand/Dorsey](https://people.csail.mit.edu/fredo/PUBLI/Siggraph2002/) 将大尺度亮度与细节分开处理；
[SLIC](https://www.epfl.ch/labs/ivrl/research/slic-superpixels/) /
[SNIC](https://www.epfl.ch/labs/ivrl/research/snic-superpixels/) 提供结构跟随区域。

作为公开对照，[HDR+ 2016](https://research.google/pubs/burst-photography-for-high-dynamic-range-and-low-light-imaging-on-mobile-cameras/)
研究欠曝、同曝光 RAW 连拍，合并后再渲染；
[后续 bracketing](https://research.google/blog/hdr-with-bracketing-on-pixel-phones/) 又加入不同曝光以改善阴影。
这些例子说明动态范围处理不限于“亮参考图上逐块贴短图”，**不说明 MotoCam 使用 HDR+**，
其 RAW 方法也不能直接等同于当前 JPEG 实现。

## 4. 两个离线小实验

修订 SPEC_02 的研究契约后，对近处固定 ROI `(3000,500,1080,1050)` 做了两个隔离实验。
它们没有进入 App，也没有通过完整验收。

1. **只柔化已有恢复边界**：以实际改变区域的内部距离、24 来源像素 smoothstep 衰减
   HDR 修正，不把数据扩展到原支持外。在来源 x=3213、y=850..1149 中，选出参考相邻
   差 <6 且相邻像素均有通道 >=247 的 295 对。边界通道最大差的中位数为：
   前 HDR **0** →后 HDR **25** →柔化 **0**；p95 后 HDR **38.3**→柔化 **1.3**。
   然而灯罩仍然白成一团，恢复范围还缩小。这是“不靠单一接缝指标验收”的反例，**不是合格修复**。
2. **离线 ROI 多尺度曝光融合**：使用原生基础合成与两张原始短图、现有全局变换，
   OpenCV Mertens 权重为 contrast=1、saturation=0、exposure=1。灯罩的上盖、侧面边缘
   与背景能分开，没有原规则方块。这表明已有观察具备可利用信息。
   但该演示**有意绕过尚未通过的逐像素局部几何 gate**，仅用于可用信息/算法方向说明；
   墙面亮度改变，灯罩内部仍近白，不具备运动、白底、颜色、普通场景或性能验收。
   不能将这张图当成“算法已完成”或“已经对标 MotoCam”。

本地忽略目录 `.tools/rc21-lamp-evidence/` 保存原包、冻结输入、测量副本、中间 native
before/after、field/gate/变换、`mask-causality.json`、`offline-ablations.json`、负载统计与图示。
原始/对照照片和可识别私人场景不提交 Git，也不进入 APK。

文件名 HDR、50 MP 尺寸、相同 CMOS、静态 APK 组件都不能确定该照片使用了哪家库、
几帧、quadtree/guided/pyramid 哪种实现，或私有参数。四文件也没有检出常见 hdrgm/MPF/
GainMap 标记；本轮不将差异归因于已证实的 Ultra HDR 增益图显示。

[Motorola 的官方 G75 规格](https://en-us.support.motorola.com/app/answers/detail/a_id/183645/~/specyfikacje--moto-g75-5g)
列出 LYTIA 600、OIS、Quad Pixel、HDR、Night Vision 与 Ultra-Res 等能力，没有说明
这四张照片实际执行的空间融合算法。已有净室 APK 研究也只支持静态组件存在，不能补齐
运行证据。本轮没有分析竞品反编译实现或移植私有参数。

合理推测是其采集、几何/时域融合和 ISP/tone mapping 的整体设计更成熟；**这仍是推测**。
看到灯罩轮廓只能证明可读边界保留得更好，不等于灯罩内部全部动态范围/纹理恢复。
Hachi 与 Moto 拍摄时间相差约一小时、取景和倍率略不同；这些参考适合定性目标，
不作为精确曝光、动态范围或分辨率优劣基准。

同传感器也不等于相同镜头、ISP、HAL 和处理权限。公开的
[Android Camera Extensions](https://developer.android.com/media/camera/camera2/extensions-api)
允许查询设备厂商暴露的 HDR/Night 等模式；当前 Ace3V/LOS 是否暴露、效果如何仍需实际查询，
不能承诺可以调用 G75 的 MotoCam 管线。

## 6. 推荐实施路线与门禁

1. **先修复支持与拒绝诊断**：区分最短帧有观察但局部几何拒绝、没有有效观察、footprint
   截断与响应/通道拒绝。研究利用周边未裁切结构验证的连续运动场；饱和内部必须有有界
   几何依据，不能靠简单膨胀或无条件接受全局变换。
2. **重叠自适应节点与连续权重**：按裁切/梯度/响应不确定性细分，保留足够上下文。
   位移冲突继续拒绝，合法重叠处权重归一，不把计算 tile 当成色调边界。
3. **分离几何、JPEG 响应和 tone mapping**：独立估计可靠响应场及不确定性；保边权重/
   增益优先 GPU，必要时使用有界多尺度融合。保护普通中间调、文字和 PPT 白底；现有
   rc15 未裁切通道保护保持，改变它之前必须再次修订契约并过负例。
4. **资源与实际效果验收**：原生网格和 ROI+halo 驻留，滤波/金字塔/重建/合成放 GPU，
   不为每张 50 MP 图建完整浮点金字塔，也不把全图 ECC 节点一律乘十六。
   对照 cold/warm 总等待、峰值内存、传输/回读、CPU/GPU 读数及失败回退；不预报手机毫秒成绩。

验收同时看：新网格边界的残差跳变、灯罩有效轮廓、灯与墙的真实边界位移、色相、噪声、
文字双边与裁切前后指标。必须有独立保留灯具/屏幕/彩色 LED、全裁切、运动、遮挡和
白底部分通道裁切负例。只模糊方块、整图压暗、关闭高光恢复或绕过物理校验均不算通过。

**可行性判断：** 这两组的轮廓改善有强输入依据，连续融合/保边权重适配 GPU 的可行性高；
完整跨场景质量、速度和 MotoCam 等效性尚未验收，不承诺所有极限光源都能恢复不存在的细节。

## 7. 50ms 诊断的首次实机结果

两组确为 rc21-1702。807/495 条采样，GPU 有效读数 806/494，丢弃均为零；
实际间隔整体中位 **50.551/50.515ms**、p95 **53.351/53.233ms**。
仅在原生处理阶段，近/远应用 CPU 可用核容量中位约 **75.65%/62.01%**，
整机 GPU 驱动忙碌窗口中位约 **10.77%/7.07%**，p95 约 **23.99%/29.67%**。
这不是 HachiCam 独占 GPU 或 shader occupancy，重复窗口不算独立新观察。
仍可见 CPU 热点与短时 GPU 活动；没有无采样的同条件对照，不能由此断言监控零开销。
