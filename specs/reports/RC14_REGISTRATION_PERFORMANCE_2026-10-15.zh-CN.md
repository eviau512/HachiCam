## 规格冲突与本轮实现

rc13 日志中 GPU 支持图执行 3 次，而 GPU 拟合提案为 0；两个真实批次均因数值
不一致回退 CPU。代码与规格还存在返回语义差异：GPU 取早先最高分的位置，CPU
返回最后更新后的位置。先修订返回/校准与资源契约，再实现以下改动。

- GPU 拟合与 CPU 的最终更新语义一致；迭代上限未收敛的 GPU 补丁回 CPU。
  保留 0.05 px /0.002 校准限和独立物理检查。GPU 物理验证失败后补做原 CPU 拟合。
- 仅将初始结构/信噪证据较强的节点作为 GPU 候选，其他节点保留原 CPU 路径，
  不修改最终资格门槛。校准区分小/中/大工作量，计入筛选、上传、同步、读回和 CPU 补齐。
  冷/热批次实测与工作量估算分开；首次校准照片的实际耗时仍包含额外对照运行。
- 每批最多 16 个补丁，分成最多 1024 样本的小块并行归约；局部中心矩和跨块均值
  修正把每轮降为两次设备调度。30 轮有界迭代在同一次提交中执行，只等待/读回一次。
- 上传打包字节，在 GPU 生成高斯、梯度和掩码五张 float 平面并复用；输入上传从
  每像素 20 字节降至 4 字节。临时平面、状态与归约仍计入 64 MiB 池及共享预留。
  实际 GPU 五张平面已与 CPU 预处理逐字节核对，检查钩子仅存在于宿主测试。
- 普通路径先完成原尺寸基准合成，再用实际 byte 图任一通道 >230 的位置限定短曝光
  拟合节点。保留全部可能影响查找的邻居，包括拒绝冲突的节点和末端夹紧节点。
  1..1023 个受支持目标像素走原全节点 admission，避免小目标被优化误丢弃。
  普通内存预估增加每源像素 4 字节覆盖新生存期重叠；流式路径保持原实现。
- 全部组统一导出到 `captures/<captureId>/`，移除 `capture/` 别名；最新/历史重复 ID
  保留最新完整版本，footer schema 2 标明目录版本、最新 ID 和有序组清单。

已通过的阶段检查不等于本轮全部最终验证；最终结果和交付状态继续补充。

## 验证与性能记录

最终检查：debug/release 各 88 项单元测试通过，standard Kotlin 编译通过；
Android debug/release 三 ABI 原生编译通过。CPU 与实际 GPU 完整图像回归通过，
GPU 五平面逐字节一致、已知位移/16 混合补丁检查通过；loader/software/pipeline/
allocation/bind/map/submit/timeout 八种失败回退通过。超时测试先完成真实任务再
模拟不可确认状态，不故意挂起驱动。归档统一、并发、淘汰与同 ID 去重检查通过。

最终十组成对运行使用两个预先加载同组冻结 BGR 的常驻进程，交替先后顺序，
OpenCV 5、四线程、OpenMP passive 等待，测试期间无其他构建/图像测试。
对照是 `d4af9ac` **纯 CPU**，实验是 rc14 自动后端；计时仅含原生调用，
并非 rc13→rc14 手机应用的完整等待对比。首轮与其余九轮分开：

| 宿主原生调用 | 旧 CPU 对照 | rc14 自动后端 |
| --- | ---: | ---: |
| 首轮 | 12.651 s | 17.388 s |
| 热运行 p50（9 次） | 18.675 s | 16.189 s |
| 热运行 p95（9 次，线性百分位） | 19.036 s | 16.653 s |

热运行 p50 相对该 CPU 对照下降 13.31%；首轮反而更慢，不能只展示较好的热数据，
也未达到 ≥30% 的实验目标。两组首轮快于后续的现象同样存在，原因没有被此测试
隔离；不能直接归因为 GPU 编译、温度或线程等待。另跑旧自动后端两次为
13.619/18.066 s，样本不足以比较版本 p50/p95。

本组每轮实际为三张 GPU 支持图、**零个 GPU 拟合提案**：拟合数值校准已相符，
小/中/大批次仍因包含筛选/CPU 补齐的成本估算选择 CPU。不能据新着色器数量
宣称本照片已实现更多 GPU 拟合或全 GPU 加速。独立合成强纹理补丁中，16 补丁热批
GPU 完整调用约 20.3–21.4 ms、CPU 34.1–36.7 ms；这只证明该内核在这类负载有收益，
不能替代本组自动策略或手机测试。
