# rc17：GPU 筛选、成本路由与逐组诊断

2026-10-16；分支 `gpu-hdr`。按照分析问题 → 分析规格 → 调整规格 → 实现验证推进。
本轮针对 [rc16 最新明亮 PPT](RC16_BRIGHT_PPT_DEVICE_2026-10-16.zh-CN.md)，
继续优先处理原生计算和 GPU 卸载，保留多帧与 rc15 白底保护。

## 问题与契约

最新手机原生耗时 26.442 s，其中全局配准 7.917 s、局部配准/验证 11.933 s；
最终等待还包含 19.017 s 队列。实际发布的 GPU 结果只有三个噪声网格、三张支持图，
没有 GPU ECC 提案或彩色合成块。不能把几毫秒的网格计算迁移称为主要负载卸载完成。

13 块 ECC 校准精度通过，GPU 冷/热为 75.403/48.648 ms、CPU 143.245 ms。
但原实现把 63.219 ms 筛选与 missing=0 时空 OpenMP 团队的 6.849 ms 一并计入，
导致成本不通过；随后又为已拒绝的类重复做了约 54/56 ms 筛选。
这是调度成本问题，不能通过降低对齐精度或直接强制 GPU 处理。宿主完整重放进一步
区分出约 147 个预合格筛选区域和首批 13 个最终拟合区域；不能混为只有 13 次相关性计算。

先修订 SPEC_02 §7.5 和 SPEC_06 GPU-SCHEDULE-17，明确冷热复用、有界重测、
筛选数学、代表区域校准、共享内存和每组决策证据；之后实现。实验参数与手机验收分开。

## 已实现

- **GPU 高通相关性筛选：** 原有便宜的方差/噪声预条件保持；候选区域的参考/源/有效性
  字节平面及已准备的高通对按最多 16 块进入共享映射缓冲区。GPU 执行字节掩码、
  10 像素边距、有效数目与中心矩归约；CPU 只做最终标量判断和数值临界区补齐。
  >=256 样本、相关性 >=0.90、比值 >=0.68 不变，筛选本身不授予图像支持。
  最初整图字节上传方案已改为仅候选区域上传，避免稀疏筛选也复制三张整图。
- **调度成本：** 冷启动额外成本按四次兼容调用摊销估计，热执行、筛选、真实缺失补齐
  均计入；实际首轮总时间仍完整记录。missing=0 不启动补齐团队。已有 CPU 类可短暂
  跳过专有筛选，成本拒绝间隔八次合格机会重测，每类每进程最多三次；数值拒绝不重试。
  0.05 px /0.002 的 ECC 一致性和原有物理检查保持。
- **profile 隔离：** 噪声区分稠密/稀疏和尺寸，支持图区分基础/高光和尺寸，拟合区分
  尺寸/用途/批量，彩色区分尺寸及 2/3/4 参考。不同类的成本和数值拒绝互不冒用。
- **彩色合成校准：** 中央、首块、末块最多三个不同代表区域核对完整 BGR 和贡献数，
  包括打包、提交、等待与歧义像素 CPU 完成成本；不再仅由边角块永久决定。
  不合算仍回 CPU，单个三缓冲区上下文和实际总分配 <=64 MiB 保持。
- **逐组证据：** 限长的后端决策、冷/热/CPU/估算成本与复用原因绑定原生结果句柄，
  Kotlin 在同步调用内取走，之后随该 captureId 的 reconstruction JSON 保留。
  避免事后读取全局“最后一张”或仅依赖会淘汰的应用尾日志。版本 3 性能包兼容旧版，
  新增筛选 GPU 块数、CPU 临界补齐块数和完整筛选时间；校准与正式发布结果分开解释。

没有启用旧 HDR shader，没有添加 UI/RAW/OCR 功能。release 保留 CPU 路径和原隐私边界。

## 验证与边界

实际 GPU 筛选与 CPU 对照覆盖非连续行、掩码、平坦/噪声、256 样本边界、相关性/比值
临界区、超过 16 块混合批和 4000×4000 来源；共享分配未越界。中心矩临界处使用相同
CPU 数学补齐。原有支持图、拟合预处理、噪声和完整彩色合成字节/贡献数回归通过。
加载器、软件设备、管线、分配、绑定、映射、提交与超时八类故障回退通过。

调度单测覆盖手机观察成本、空缺失、有界重试、数值拒绝、profile 隔离、句柄一次消费、
截断/失败清空与并行拍摄证据隔离。CPU 和实际 GPU 全图 HDR/SR、遮挡/视差、噪声与
文档边界回归通过。debug/release 各 90 项单测，standard Kotlin 和两种模式三 ABI 编译通过。

最新 PPT 冻结七张 BGR 输入，rc16/rc17 纯 CPU 与自动后端首轮成片四者逐字节相同：
`804421e6537cfdca9b6db1e0021202ab7f7db3519828ccfdd36381a83d10b8b9`。
均选择参考 1、8044×5996、相同裁切，196 块合格、实际改动 1.5691%；宿主 OpenCV 与
手机 199 块的差别没有掩盖为同一实现环境。旧远拍 PPT 的 rc17 CPU 成片仍保持原基准
`ec7acef0bda3290b764a330f21e89e874636cef6a5ce2800db0ddbd1d8f03502`。

预加载同组输入、四线程、交错十组普通自动后端，包含校准/传输/补齐；不强制 GPU：

| 宿主原生指标 | rc16 | rc17 |
| --- | ---: | ---: |
| 首轮 | 13.458 s | 19.480 s |
| 后九次热 p50 | 16.304 s | 16.191 s |
| 后九次热 p95 | 16.646 s | 16.812 s |
| 全局配准热 p50 | 5.880 s | 5.910 s |
| 局部配准/验证热 p50 | 4.524 s | 4.517 s |

热 p50 只低 **0.69%**，p95 和首轮更慢，不能声称有稳定或显著提速，未达到 ≥30% 目标。
单次冷调用与长时热状态也不能合并解释为确定的算法倍率。本轮验证重点是实际路由和
图像不退步，主要配准负载仍未移走；新版本的手机结果必须独立检验。

这次 rc17 普通路径实际发布五张 GPU 支持图、每轮 192 个 GPU 彩色合成块；噪声网格
从前几轮的四个，经有界重新校准后增至七个。彩色合成热 p50 约 648.639 ms；首轮
12,057,956 个原生像素中 1,679,095 个数值歧义由 CPU 完成，不能把它们算作独立 GPU
结果。新筛选虽实际跑过校准，但成本仍选 CPU；正式 GPU 筛选/ECC 提案计数均零。
较大拟合类发生数值拒绝，仍被阻断；未以增加占用率为理由放宽 0.05 px /0.002。
这些是电脑上的实测选择，不预设手机将采用相同后端。

## 仍需做

全局 EUCLIDEAN/HOMOGRAPHY ECC、候选结构验证、局部物理检查和区域迭代仍有较大
CPU 负载。后续应按整块驻留/归约迁移，减少 CPU/GPU 往返；不能用强制 GPU 开关或
降低资格门槛冒充提速。本轮新增核与路由修正不等于已经完成这些热点。

手机首轮/热态完整等待、实际采用的拟合/筛选/合成数、峰值内存和温度仍待新 APK 实测。
宿主使用 Windows Vulkan 与 OpenCV 5，手机使用 Android/Adreno 与 OpenCV 4.10，
宿主计时不能替代手机 ≥30% 性能目标。PPT 细字和卧室灯具 HDR 仍未宣称全部验收。
